# RSI Knowledge Dashboard

A scientific knowledge dashboard is only worth having if its claims are true. The core rule of this skill is:

> **The model writes. Code decides what counts as verified. The page only shows what actually happened.**

Most failures this skill exists to prevent looked successful: hard-coded `PASS` labels, template text called research, fake sample papers used when a search failed, and passes that did nothing.

## Workflow

### 1. Settle the decisions

Ask only what you cannot default. Each answer is a line in `project.json`.

| Decision | Default | Why it matters |
|---|---|---|
| Topic and audience | Ask | Sets the source mix |
| Output language | `en` or `zh-TW` | Sets the deck, blog and infographic language |
| Model provider | `claude` | See `references/platform-adapters.md` |
| Sources | Literature, arXiv, local PDFs | Add ClinicalTrials.gov for clinical topics; add a NotebookLM ID if there is one |
| Sensitive data | None | If patient or personal data is near this project, read "Privacy" below first |
| Required terms | None | Fill `terms` for fields with a standard translation; models get these wrong |

### 2. Scaffold

```bash
python <this-skill>/scripts/scaffold.py ./my-dashboard --title "..." --topic "..." --language en
```

It uses only the standard library and refuses to write into a non-empty folder. Add `--clinical-trials` for clinical topics and `--provider openai_compatible` for non-Claude models.

### 3. Configure

- Put reference PDFs in `references/`.
- Edit `project.json`: `writer_role`, `terms`, `sources`, `provider`.
- Add known identifiers to `.phi_blocklist.txt`.
- Put secrets in `.env`, never in `project.json`.

### 4. Verify before calling it working

Run these in order. Do not skip step 3 because the API tests pass: browser form validation is invisible to them, and it once blocked every submission.

```bash
# 1. Install and check, spending nothing
uv run --no-project --python 3.12 --with-requirements requirements.txt python run_agent.py --check

# 2. Offline tests with a scripted model
uv run --no-project --python 3.12 --with-requirements requirements.txt --with pytest python -m pytest tests/test_agent.py -q

# 3. Start the server in one terminal, then drive it in a real browser (spends nothing)
./start_dashboard.sh    # Windows: .\start_dashboard.ps1
uv run --no-project --python 3.12 --with playwright python tests/browser_smoke.py
```

Then do one **small live run** with the cheapest model, one or two passes and a low budget. **Read and look at the outputs yourself.** Checks do not catch everything: broken reference names, mistranslated terms and internal keys in the prose were all found by reading, and each then became a check.

Report honestly: what ran, what each source really did, what it cost, and what was not tested.

### 5. Hand over

Tell the user how to start it, which sources are live, and what `VERIFIED` does and does not mean. Offer to fix anything marked unavailable, and never describe a source as connected unless it returned data in a real run.

## How the loop works

```
plan searches -> collect evidence -> privacy gate -> write the paper -> code checks -> repair (same conversation)
      ^                                                                                     |
      |                 reviewer critique -> gaps and new queries <-------------------------+
      |                                                                                     |
      +------------------------------------ next pass                                      v
                                                     slides, blog, infographic -> code checks -> repair
                                                                                            |
                                                     online citation lookup -> run report <-+
```

Details are in `references/architecture.md`. Rules are in `references/verification-rules.md`.

## Hard rules

1. **No fake success.** A source that fails contributes nothing and says so. A missing provider raises an error. Never ship built-in "sample" papers, and never return mock text as if a model wrote it.
2. **No hand-typed citations.** The model cites `[E3]`; code builds the references from collected metadata.
3. **A DOI that exists is not enough.** Compare its registered title with the paper you mean. Real DOIs can belong to unrelated papers.
4. **Every status on the page comes from a run.** No static `PASS`, no hard-coded counts, no "active" badge that nothing sets.
5. **Every setting must change something.** If a passes selector, topic or model field has no effect, remove it or make it work. Test this.
6. **Never overwrite earlier results.** Each run gets its own folder.
7. **A spending limit must be real.** Refuse to run a paid endpoint whose cost cannot be computed.
8. **Paid or destructive endpoints accept only their own origin**, on localhost, with JSON. Never open CORS to make a local-file page work.
9. **A learned rule is kept only on measured evidence**: its failure stopped and overall fitness rose. Otherwise record the rejection.
10. **`VERIFIED` is scoped.** It means sources and figures trace correctly. It does not mean the interpretation is right. The page must say so, and a qualified person reviews before use.

## Privacy

If patient, personal or confidential data is anywhere near the project:

- Do not read raw records unless the task requires it. Sources and outputs both pass the identifier gate.
- `.phi_blocklist.txt` is a safety net for names you already know. **It is not de-identification** and does not establish HIPAA compliance. Never write "HIPAA PASS" based on it.
- Evidence is sent to the model provider. Confirm that is allowed before including any case material.
- Before any push, scan the **exact files being pushed**, including notes, wrap-ups and old versions. A note describing how identifiers were removed can itself contain them.
- If identifiers reach a public repository, make it private first, then clean history, and tell the responsible privacy officer. Deleting the file is not enough.

## Sources with no API

Do not pretend. For a service that needs a signed-in browser, the template writes `questions_to_ask.md` and reads answers saved to `references/saved_answers/`, labelled as secondary evidence. Browser automation is possible but needs the user's login and a check of that service's terms, so it is the user's decision.
